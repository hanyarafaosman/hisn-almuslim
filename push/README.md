# خادم تنبيهات الصلاة (والتطبيق مغلق)

صفحة الويب لا تشتغل إلا والمتصفح فاتحها، والهاتف بيوقف التطبيقات المقفولة. عشان كده التذكير قبل الصلاة وإشعار دخول الوقت بيوصلوا والتطبيق مقفول عن طريق **Web Push**: خادم صغير على **Cloudflare Workers** مع قاعدة بيانات **D1**، بيحسب نفس المواقيت بملف التطبيق نفسه (`www/js/prayer-calc.js`، مستورد مش منسوخ) وبيبعت رسالة قصيرة في وقت كل تنبيه.

| الملف | الاستخدام |
|---|---|
| `src/index.js` | الخادم: `POST /subscribe` و`DELETE /unsubscribe` و`GET /health`، والمهمة اللي بتشتغل كل دقيقة |
| `src/schedule.js` | التنبيه الجاي لكل مشترك (نفس منطق `www/js/prayer.js`) والتحقق من الإعدادات |
| `src/webpush.js` | VAPID (RFC 8292) وتشفير الرسالة aes128gcm (RFC 8291) بـ WebCrypto بس، من غير مكتبات |
| `migrations/0001_subs.sql` | جدول المشتركين |
| `keys.js` | مفتاحا VAPID: العام للتطبيق، والخاص يتحط سرًّا في الخادم وبس |
| `test.js` | اختبارات من غير إنترنت ولا Cloudflare (`npm test`، وبتشتغل مع `npm run check` في جذر المشروع) |

## إزاي بيشتغل

1. لما المستخدم يفعّل التنبيهات ويسمح بالإشعارات، `www/js/prayer.js` بيعمل اشتراك Push في المتصفح وبيبعت للخادم: الاشتراك، والمكان **مقرّب لـ 0.01° (حوالي كيلومتر)**، والمنطقة الزمنية، وجهة الحساب والعصر وتعديلات الدقائق والتاريخ الهجري، وتنبيه كل صلاة، ودقائق التذكير، ولغة الواجهة. وبيبعتها تاني مع أي تغيير، ومرة في اليوم على الأكثر لو مفيش تغيير.
2. الخادم بيحسب التنبيه الجاي ويحفظه (`next_at`). كل دقيقة بياخد التنبيهات اللي جه وقتها ويبعت لكل واحد رسالة مشفّرة `{ p, at, kind, l }`: الصلاة، ووقتها، ونوع التنبيه (`before` أو `notify` أو `adhan`)، واللغة. وبعدين بيحسب التنبيه اللي بعده.
3. الـ service worker (`www/sw.js`) بيكتب الإشعار بنصوص التطبيق بلغة المستخدم («حان الآن وقت صلاة الظهر»، «الظهر بعد 5 دقائق») مع الساعة واسم المكان المحفوظين على الجهاز. لو التطبيق قدامك على الشاشة، هو اللي بيعرض التنبيه، ولو كان عرضه وهو في الخلفية، الإشعار مش بيتكرر.
4. **الإشعار مايقدرش يشغّل تسجيل الأذان.** الضغط عليه بيفتح التطبيق، والتطبيق بيرفع الأذان لو المتصفح سمح (خلال 3 دقائق من دخول الوقت، زي ما كان)، وإلا بيظهر زر «رفع الأذان».
5. إيقاف التنبيهات بيمسح الاشتراك من الخادم. ولو المتصفح أنهى الاشتراك (مسح البيانات أو إزالة التطبيق)، خدمة الإشعارات بترد 404/410 والخادم بيمسح الصف.

المكان على الجهاز بقى بيتحسب برضه مقرّب لـ 0.01°، عشان التطبيق والإشعار يقولوا نفس الدقيقة بالظبط (الفرق ثواني، والأوقات أصلًا بالدقيقة).

## التشغيل لأول مرة

محتاج حساب Cloudflare (مجاني) وNode 22 أو أحدث. كل الأوامر من مجلد `push/`:

```bash
cd push
npm install
npx wrangler login
```

`wrangler login` بيفتح المتصفح وتوافق بحسابك. بعدها:

```bash
npx wrangler d1 create hisn-push
```

انسخ الـ `database_id` اللي بيطبعه مكان الأصفار في `wrangler.toml` (مش سر، عادي يتحط في git). وبعدين:

```bash
npm run db:remote
npm run deploy
npm run keys
npm run deploy
```

- `db:remote` بيعمل الجدول في D1.
- أول `deploy` بيعمل الخادم على `https://hisn-push.<اسمك>.workers.dev`.
- `keys` بيعمل مفتاحي VAPID: **الخاص بيروح على طول لسر الخادم** (`wrangler secret put VAPID_PRIVATE_KEY`) ومش بيتكتب في أي ملف، والعام بيتكتب في `wrangler.toml` و`www/js/prayer.js`.
- تاني `deploy` عشان الخادم ياخد المفتاح العام.

آخر خطوة: حط عنوان الخادم في `PUSH.url` في `www/js/prayer.js` (`scripts/check-sources.js` بياخده من هناك)، وارفع إصدار التطبيق، وانشر.

الخادم الحالي: `https://hisn-push.hisn-push.workers.dev` على حساب hanyarafaosman. لو غيّرت اسم الـ workers.dev subdomain من لوحة Cloudflare، العنوان هيتغيّر، ولازم يتغيّر في `PUSH.url` وتنشر التطبيق.

لو المفتاح الخاص ضاع أو اتسرب: `npm run keys` تاني و`npm run deploy` وانشر التطبيق. كل متصفح بيلاحظ إن المفتاح اتغيّر ويشترك من جديد لوحده أول ما التطبيق يتفتح، ولحد ما يتفتح الإشعارات مش هتوصله.

## الحدود والتكلفة

الخطة المجانية لـ Workers كفاية لعدد كبير، بس فيها حدود لازم تعرفها:

| الحد (مجاني) | الأثر |
|---|---|
| 50 طلبًا للخارج في كل تشغيل | رسالة الإشعار طلب. عشان كده `MAX_PUSH = 40` رسالة في الدقيقة، والباقي بيتأخر دقيقة ورا دقيقة. الزحمة بتبقى لما ناس كتير في نفس المدينة ونفس الإعدادات: الصلاة بتيجي لهم في نفس الدقيقة |
| 10 مللي ثانية من وقت المعالج في كل تشغيل | التشفير بياخد جزء صغير من المللي ثانية للرسالة، وده كمان سبب إن الحد 40 |
| 100,000 طلب في اليوم | المهمة كل دقيقة = 1440، وكل جهاز بيبعت إعداداته مرة في اليوم على الأكثر |
| D1: ‏100,000 كتابة و5 ملايين قراءة في اليوم | كل تنبيه بيتبعت = كتابة واحدة تقريبًا (11 في اليوم لكل جهاز بالتذكير)، يعني حوالي 4,000 جهاز |

لو المستخدمين كتروا وبقت الإشعارات بتتأخر، **خطة Workers Paid (‏5 دولار في الشهر)** بتخلي الحد 10,000 طلب و30 ثانية معالج في التشغيل: ارفع `MAX_PUSH` في `wrangler.toml` (مثلًا 2000) و`npm run deploy`. الحل الأكبر بعد كده Cloudflare Queues لتوزيع الإرسال على أكتر من تشغيل.

التنبيه اللي يتأخر أكتر من 10 دقائق (أو التذكير اللي وقت صلاته جه) بيتشال من غير ما يتبعت، عشان محدش يوصله «حان وقت الظهر» بعد نص ساعة.

## المتابعة

- `GET /health` بيرد `{ ok, cron }`: `cron` هو آخر مرة المهمة اشتغلت. `npm run check:sources` في جذر المشروع (كل يوم على GitHub) بيفشل لو الخادم مابيردش أو المهمة واقفة من أكتر من 10 دقائق.
- `npm run logs` بيعرض سجل الخادم مباشرة: كل دقيقة فيها تنبيهات بتطبع `{ due, sent, gone, retry, late }`. والسجلات كمان في لوحة Cloudflare (Workers → hisn-push → Logs).

## التجربة على جهازك

```bash
npm run keys -- --dev
npm run db:local
npm run dev
```

- `keys -- --dev` بيعمل مفتاحين للتجربة في `push/.dev.vars` (خارج git).
- `dev` بيشغّل الخادم على `http://localhost:8787`. المهمة مش بتشتغل لوحدها محليًا: اطلبها بـ `curl "http://localhost:8787/__scheduled?cron=*+*+*+*+*"`.
- افتح التطبيق من `npm run dev` في جذر المشروع مع `?sw` (عشان الـ service worker يشتغل على localhost)، واكتب في الـ console السطر اللي طبعه `keys -- --dev` (`localStorage.pushServer = …`)، وفعّل التنبيهات.
